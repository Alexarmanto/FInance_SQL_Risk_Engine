# SQL-first Trade & Risk Analytics

A trade & risk analytics project where **SQL is the analytical engine, not a storage layer**.
Every business calculation — positions, P&L, historical VaR, anomaly detection, corporate-action
adjustments, reconciliation, concentration risk, performance ranking — is implemented as a SQL
query against a SQLite database. Python is used exclusively to (1) generate realistic synthetic
market/trading data and (2) execute and display the SQL results with pandas. **No business metric
is computed or recomputed in pandas/NumPy anywhere in this repo.**

This is a portfolio project aimed at demonstrating SQL fluency for quant/risk/data engineering
roles: window functions, recursive CTEs, manual statistical primitives (percentile, standard
deviation) in a database that doesn't provide them natively, query-plan-driven optimization, and
clean multi-CTE query design.

## Why this project exists

Most "SQL + pandas" portfolio projects load data into a DataFrame and do the actual math there,
using SQL only to `SELECT * FROM table`. This project inverts that: SQL owns running totals,
moving averages, percentiles, standard deviations, recursive compounding, and set-based
reconciliation. pandas only ever touches a result set that SQL has already fully computed, to
print it as a table.

## Stack

- **SQLite** via Python's built-in `sqlite3` — zero external DB dependency.
- **Python 3** (`numpy`, `random`, `datetime`) for synthetic data generation only.
- **pandas** for *display formatting only* (`analysis.py`), never for calculation.

## Database schema

| Table                 | Grain                              | Rows (generated) |
|------------------------|-------------------------------------|-------------------|
| `instruments`           | 1 row / tradable instrument         | 40                |
| `clients`                | 1 row / client                      | 25                |
| `trades`                 | 1 row / executed trade              | 42,000            |
| `market_data`             | 1 row / instrument / trading day    | 21,000 (2 years)  |
| `corporate_actions`       | 1 row / split or dividend event     | 9                 |
| `declared_positions`      | 1 row / client / instrument (custodian snapshot) | ~994 |

```
instruments(id, ticker, name, sector, asset_class, currency)
clients(id, name, client_type, opening_date)
trades(id, client_id -> clients, instrument_id -> instruments,
       timestamp, quantity, price, side)
market_data(instrument_id -> instruments, timestamp, close_price, volume)
corporate_actions(id, instrument_id -> instruments, date, action_type, ratio)
declared_positions(client_id, instrument_id, reference_date, declared_quantity)
```

Full DDL, with the baseline/optimized index split documented inline, lives in [schema.sql](schema.sql).

### Synthetic data, briefly

- **Instruments**: 40, spread evenly across 10 sectors, 3 asset classes (Equity/ETF/Bond),
  4 currencies.
- **Clients**: 25, mixed `Individual` / `Corporate` / `Institutional`, ~55% deliberately
  *concentrated* on one home sector, the rest diversified — so sector-concentration queries
  produce contrasted, non-trivial results.
- **Market data**: 2 years of daily closes per instrument via a **geometric Brownian motion**
  with per-instrument drift, and a **Markov-switching volatility regime** (calm/normal/turbulent,
  97% daily persistence) so realized volatility clusters in time instead of being flat noise.
  Split events are applied as genuine multiplicative price jumps on the action date, exactly as a
  raw (unadjusted) price series would show them.
- **Trades**: 42,000, generated by walking the trading calendar day by day with a real holdings
  ledger (a SELL can never exceed current holdings). Volume is deliberately non-uniform: monthly
  seasonality (e.g. a quiet August, an active January/October), a mild day-of-week effect, and ~10
  random "burst weeks" with 2–4x elevated activity.
- **Corporate actions**: 9 events — 6 SPLITs across 5 instruments (one instrument gets **two**
  successive splits, to exercise the recursive-CTE compounding) and 3 DIVIDEND events.
  Critically, a split silently multiplies a holder's economic position **without inserting a
  trade row** (exactly like in real life) — which is *why* the raw running-total position
  (query 1) and the corporate-action-adjusted position (query 6) genuinely diverge, rather than
  being adjusted for cosmetic reasons.
- **declared_positions**: seeded from the correct corporate-action-adjusted position (computed
  in SQL — see `generate_data.py::REFERENCE_POSITION_SQL`), then deliberately corrupted: 6
  quantity mismatches, 4 rows dropped (missing at the custodian), 4 phantom rows added. Query 7
  finds exactly these 14 breaks.

Regenerate everything with:
```bash
python generate_data.py
```

## The 9 queries

All under [queries/](queries/), one file each, fully commented with the reasoning inline. Every
query runs standalone against `data/risk_engine.db`.

| # | File | SQL technique demonstrated |
|---|------|------------------------------|
| 1 | [01_position_running_total.sql](queries/01_position_running_total.sql) | Running-total **window function** — `SUM() OVER (PARTITION BY client_id, instrument_id ORDER BY timestamp)` reconstructs cumulative position per book with zero procedural code. |
| 2 | [02_pnl_realized_unrealized.sql](queries/02_pnl_realized_unrealized.sql) | **Chained CTEs** implementing moving-average-cost accounting: running buy-cost/buy-quantity → average acquisition cost → realized P&L per SELL → latent P&L on the still-open position, joined against the latest market price. |
| 3 | [03_var_historical.sql](queries/03_var_historical.sql) | **Historical VaR** via an event-time "as-of" running `SUM()` that forward-fills daily positions onto a calendar without a correlated subquery, `LAG()` for daily returns, and a manual **percentile** (`ROW_NUMBER()`/`COUNT()` over a sorted window) since SQLite has no `PERCENTILE_CONT`. |
| 4 | [04_zscore_anomaly_detection.sql](queries/04_zscore_anomaly_detection.sql) | Rolling **z-score anomaly detection**: `AVG() OVER` a bounded frame for the rolling mean, and a manual rolling **standard deviation** from `E[X²] − E[X]²` (SQLite has no `STDEV` window function), flagging trades `> 3σ` from a 20-trade rolling mean. |
| 5 | [05_corporate_actions_recursive_factor.sql](queries/05_corporate_actions_recursive_factor.sql) | **`WITH RECURSIVE`** CTE composing an ordered sequence of split/dividend events into a cumulative adjustment factor (two successive splits compound multiplicatively). |
| 6 | [06_position_adjusted_corporate_actions.sql](queries/06_position_adjusted_corporate_actions.sql) | Reuses query 5's recursive factor and **joins** it back onto every historical trade (with a `COALESCE`d conditional join for instruments with no corporate action) to restate quantities in today's share-count terms. |
| 7 | [07_reconciliation.sql](queries/07_reconciliation.sql) | **Position reconciliation** against a simulated second source of truth, emulating a `FULL OUTER JOIN` via two `LEFT JOIN`s combined with `UNION` — a portable pattern that catches breaks on both sides (missing / phantom / mismatched). |
| 8 | [08_sector_concentration.sql](queries/08_sector_concentration.sql) | Multi-level **CTE aggregation** (per client+sector, then per client) to compute exposure percentages without materializing an intermediate total in Python; flags >40% single-sector concentration. |
| 9 | [09_performance_ranking.sql](queries/09_performance_ranking.sql) | **`RANK()` / `DENSE_RANK()`** window functions ranking clients by portfolio return, side by side to make the gap-vs-no-gap tie-breaking behavior explicit. |

### SQLite gaps this project works around, in SQL

SQLite deliberately ships a minimal SQL surface. Rather than dropping to pandas whenever a
built-in was missing, every gap below is closed with a documented, standard SQL pattern:

- **No `PERCENTILE_CONT` / `PERCENTILE_DISC`** → query 3 sorts returns with `ROW_NUMBER()` and
  selects the rank matching the target percentile.
- **No `STDEV` / `STDEV_POP` window function** → query 4 derives it manually from
  `AVG(x²) − AVG(x)²`, guarded with `MAX(variance, 0)` against floating-point rounding.
- **No native forward-fill** for "position as of any calendar date" → query 3 unions trade events
  with zero-delta calendar markers and reads a running `SUM()` back out, instead of N correlated
  subqueries.
- **No `FULL OUTER JOIN`-required semantics assumed portable** → query 7 uses the classic
  two-`LEFT JOIN`-plus-`UNION` emulation.

## Running it

```bash
python generate_data.py   # builds data/risk_engine.db from scratch (baseline schema, no secondary indexes)
python analysis.py        # runs all 9 queries + the optimization section, prints everything,
                           # then exports figures/*.png and results/*.csv
```

No external dependencies beyond `numpy`, `pandas`, and `matplotlib`
(`pip install numpy pandas matplotlib`) — the database layer is the Python standard library's
`sqlite3`.

## Optimization: EXPLAIN QUERY PLAN + measured timing

The 3 heaviest queries all run a **window function over the full `trades` table**, requiring rows
sorted by `(partition columns..., timestamp)`. `generate_data.py` intentionally creates the
database with **no secondary indexes** (see `schema.sql`, section 1 vs. section 2), so
`analysis.py` can measure the real before/after effect of adding them.

**Why it was slow:** without a matching index, SQLite has to materialize the partition/order key
into a temporary B-tree to sort it before the window function can stream through it — visible in
`EXPLAIN QUERY PLAN` as `USE TEMP B-TREE FOR ORDER BY`.

**What was added** (from `schema.sql`, applied live by `analysis.py`):
```sql
CREATE INDEX idx_trades_client_instrument_ts ON trades (client_id, instrument_id, "timestamp");
CREATE INDEX idx_trades_instrument_ts        ON trades (instrument_id, "timestamp");
CREATE INDEX idx_corporate_actions_instrument_date ON corporate_actions (instrument_id, date);
CREATE INDEX idx_market_data_instrument_ts   ON market_data (instrument_id, "timestamp");
```

With a composite index matching `(PARTITION BY ..., ORDER BY ...)`, SQLite scans the table
already in the required order and the `USE TEMP B-TREE FOR ORDER BY` step disappears from the
plan — e.g. query 1's plan changes from `SCAN t` to `SCAN t USING INDEX idx_trades_client_instrument_ts`.

**Measured result** (7 runs each, median wall-clock, `time.perf_counter()`; see `analysis.py`
for the exact methodology — a representative run is shown below):

| Query | Median before | Median after | Gain |
|-------|---------------|--------------|------|
| Query 1 — running-total position | 0.153s | 0.116s | **~24%** |
| Query 4 — z-score anomaly detection | 0.081s | 0.062s | **~24%** |
| Query 3 — historical VaR | 1.453s | 1.367s | **~6%** |

(Run-to-run variance on a laptop is normal — repeat runs typically land in the 5–40% range for
these three queries depending on system load; the query-plan change described above is the
deterministic part of the story, the percentage is not.)

Query 3 benefits both from the trades index (removes the sort feeding its `UNION ALL` branch) and
from `idx_market_data_instrument_ts` (the calendar/price join becomes a covering-index scan
instead of hitting the implicit rowid-based PK index).

**Honest caveat on scale**: at ~42k trades / ~21k market_data rows, SQLite's whole working set
sits comfortably in the OS page cache, so the *absolute* wall-clock gain is modest even though the
query plan is structurally cheaper (an O(n log n) sort removed from the plan). At real production
row counts, the eliminated sort would dominate far more and the relative gain would widen
considerably — the query-plan change is the reliable signal here, not just the millisecond delta.
